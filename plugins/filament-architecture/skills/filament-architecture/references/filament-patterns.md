# Filament v4/v5 seams

Every Filament extension point that changes data, and how to hand that work to a use case. v4 and v5 share this API (v5 = v4 + Livewire 4). When a signature here doesn't match the installed version, grep `vendor/filament` — it is the source of truth.

## 1. Namespaces (v4/v5)

| Thing | Namespace |
|---|---|
| Every action (page, table row, bulk, header) | `Filament\Actions\{Action, BulkAction, CreateAction, EditAction, DeleteAction, ...}` |
| Form schema container | `Filament\Schemas\Schema` (`form(Schema $schema): Schema`) |
| Form fields | `Filament\Forms\Components\*` |
| Layout (Section, Grid, Tabs, Wizard) | `Filament\Schemas\Components\*` |
| Table | `Filament\Tables\Table` |
| UI notifications | `Filament\Notifications\Notification` |

Resource layout generated by v4: `app/Filament/Resources/Orders/OrderResource.php`, `Pages/`, `Schemas/OrderForm.php`, `Tables/OrdersTable.php`.

Action modal fields go in `->schema([...])`.

## 2. Error mapping

Use cases throw `App\Domain\Shared\DomainException` subclasses with user-safe messages. At the Filament boundary, catch exactly that type:

```php
try {
    $useCase->execute($input);
} catch (DomainException $e) {
    Notification::make()->danger()->title($e->getMessage())->send();
    $action->halt();   // in actions: stop, keep the modal open
    // $this->halt();  // in page lifecycle methods (Create/Edit pages)
}
```

`$action->cancel()` stops and closes the modal instead — use it when retrying makes no sense. Do not catch `\Throwable`; real failures should surface.

Filament can wrap actions in a database transaction (panel-level `->databaseTransactions()` or per-action `->databaseTransaction()`; `halt()`/`cancel()` accept `shouldRollBackDatabaseTransaction: true`). Don't rely on that for business atomicity — the use case must be atomic on its own through `TransactionManager`, because it will also run from places that aren't Filament. The two nest safely (Laravel uses savepoints).

If many actions repeat this try/catch, extract a tiny helper in the Filament layer (e.g. a trait `RunsUseCases` with `runUseCase(callable $fn, Action $action)`), never in the Application layer.

## 3. Row / header actions

```php
Action::make('cancel')
    ->color('danger')
    ->requiresConfirmation()
    ->authorize('cancel')
    ->visible(fn (Order $record): bool => $record->status->canBeCancelled())
    ->schema([
        Select::make('reason')->options(CancellationReason::class)->required(),
    ])
    ->action(function (Order $record, array $data, Action $action, CancelOrder $cancelOrder): void {
        try {
            $cancelOrder->execute(new CancelOrderInput(
                orderId: $record->getKey(),
                cancelledBy: auth()->id(),
                reason: CancellationReason::from($data['reason']),
            ));
        } catch (DomainException $e) {
            Notification::make()->danger()->title($e->getMessage())->send();
            $action->halt();
        }

        Notification::make()->success()->title('Order cancelled')->send();
    });
```

Notes:
- Closure parameters are injected by name/type: `$record`, `$data`, `$action`, `$livewire`, plus any container-resolvable class — that is how the use case arrives.
- `visible()` asks the domain enum; the use case re-checks the same rule. The UI check is a convenience, the use case is the guard (a stale page can still submit).
- Pass ids, not the Livewire-held model, into strict-mode use cases; the repository re-reads fresh state.

## 4. Create page

```php
use Illuminate\Database\Eloquent\Model;

final class CreateOrder extends CreateRecord
{
    protected static string $resource = OrderResource::class;

    protected function handleRecordCreation(array $data): Model
    {
        try {
            $result = app(PlaceOrder::class)->execute(new PlaceOrderInput(
                customerId: (int) $data['customer_id'],
                lines: array_map(
                    fn (array $line) => new OrderLineInput((int) $line['product_id'], (int) $line['quantity']),
                    $data['lines'] ?? [],
                ),
                placedBy: auth()->id(),
            ));
        } catch (DomainException $e) {
            Notification::make()->danger()->title($e->getMessage())->send();
            $this->halt();
        }

        return Order::findOrFail($result->orderId); // Filament needs a model for redirect/notification
    }
}
```

- `handleRecordCreation()` must return a Model. In strict mode re-read it by id; in pragmatic mode the use case can return the model.
- Move logic out of `mutateFormDataBeforeCreate()`, `beforeCreate()`, `afterCreate()` too. Pure shape changes (renaming keys, casting strings) may stay in `mutateFormDataBeforeCreate()`; anything that computes a business value (order number, totals, due date) goes into the use case.
- If the form uses `->relationship()` on repeaters/selects, Filament saves those relations itself *after* `handleRecordCreation()`. When those relations carry business meaning (order lines with prices), remove `->relationship()` and let the use case create them from `$data`.

## 5. Edit page

```php
protected function handleRecordUpdate(Model $record, array $data): Model
{
    try {
        app(UpdateOrderDetails::class)->execute(new UpdateOrderDetailsInput(
            orderId: $record->getKey(),
            shippingAddress: $data['shipping_address'],
            customerReference: $data['customer_reference'] ?? null,
        ));
    } catch (DomainException $e) {
        Notification::make()->danger()->title($e->getMessage())->send();
        $this->halt();
    }

    return $record->refresh();
}
```

**Status fields don't belong in edit forms.** A `Select::make('status')` on an edit form turns every state transition (approve, ship, cancel, refund) into "save whatever the user picked", with no preconditions and no side effects. Replace it with explicit header actions (`ApproveOrder`, `ShipOrder`, ...) and show status as a read-only badge/placeholder. Plain descriptive fields (address, notes) can stay in an "update details" use case.

Exception: in a refactor where the user asked for behaviour to stay identical, keep the select for now, make `handleRecordUpdate()` detect the status change and dispatch to the matching transition use case, and recommend the switch to explicit actions as the next step.

Also check `afterSave()` / `beforeSave()` — they are a favourite hiding place for emails and recalculations.

## 6. CreateAction / EditAction in modals and relation managers

These write to Eloquent by default. Route through a use case with `->using()`:

```php
use Filament\Resources\RelationManagers\RelationManager;

CreateAction::make()
    ->using(function (array $data, CreateAction $action, RelationManager $livewire, AddOrderLine $addOrderLine): Model {
        try {
            $result = $addOrderLine->execute(new AddOrderLineInput(
                orderId: $livewire->getOwnerRecord()->getKey(),
                productId: (int) $data['product_id'],
                quantity: (int) $data['quantity'],
            ));
        } catch (DomainException $e) {
            Notification::make()->danger()->title($e->getMessage())->send();
            $action->halt();
        }

        return OrderLine::findOrFail($result->orderLineId);
    });
```

`EditAction::make()->using(fn (Model $record, array $data) => ...)` works the same way. For `AttachAction`, `DetachAction`, `AssociateAction`, `DissociateAction`: if attaching has rules or side effects (seat limits, prorated billing), replace them with a plain `Action` that calls a use case — their default behaviour is a raw relationship write.

## 7. Bulk actions

```php
BulkAction::make('approve')
    ->requiresConfirmation()
    ->authorizeIndividualRecords('approve')
    ->action(function (Collection $records, ApproveOrder $approveOrder): void {
        $failed = [];

        foreach ($records as $order) {
            try {
                $approveOrder->execute(new ApproveOrderInput($order->getKey(), auth()->id()));
            } catch (DomainException $e) {
                $failed[] = "#{$order->getKey()}: {$e->getMessage()}";
            }
        }

        $failed === []
            ? Notification::make()->success()->title('Orders approved')->send()
            : Notification::make()->warning()->title(count($failed).' not approved')->body(implode("\n", $failed))->send();
    })
    ->deselectRecordsAfterCompletion();
```

If the whole batch must succeed or fail together, write a batch use case (`ApproveOrders` taking a list of ids) that uses `TransactionManager`, instead of looping in Filament. For large selections add `->chunkSelectedRecords(250)` (records become a `LazyCollection`).

## 8. Inline-editable columns

`ToggleColumn`, `SelectColumn`, `TextInputColumn` and `CheckboxColumn` save straight to the model on change. For cosmetic fields that's fine. For anything with business meaning (`is_active` that should revoke access, `price`, `status`):

- preferred: replace the column with a read-only column + an action, or
- route it: editable columns have `->updateStateUsing(Closure)` (in `Filament\Tables\Columns\Concerns\CanUpdateState`), which replaces the default set-attribute-and-`save()`. Call the use case there and return the new state:

```php
ToggleColumn::make('is_active')
    ->disabled(fn (Customer $record): bool => ! auth()->user()->can('update', $record))
    ->updateStateUsing(function (Customer $record, bool $state, SetCustomerActive $setActive): bool {
        $setActive->execute(new SetCustomerActiveInput($record->getKey(), $state, auth()->id()));

        return $state;
    }),
```

Two traps: `beforeStateUpdated()` / `afterStateUpdated()` run *around* the default Eloquent write, so business logic there keeps the write in Filament; and inline-editable columns **do not check model policies** — only `disabled()` is respected — so guard them explicitly as above. If the use case can throw a `DomainException`, prefer an action instead: a toggle has no good place to show the error.

## 9. Importers

Each CSV row goes through `resolveRecord(): ?Model` → `fillRecord(): void` → `saveRecord(): void` (all public on `Filament\Actions\Imports\Importer`), with hooks (`beforeSave`, `afterCreate`, ...) around them. If importing is just loading data, the default is fine. If rows must obey business rules, override `saveRecord()` so each row goes through the use case, and convert domain errors into row failures:

```php
use Filament\Actions\Imports\Exceptions\RowImportFailedException;

public function saveRecord(): void
{
    try {
        $result = app(RegisterProduct::class)->execute(new RegisterProductInput(
            sku: (string) $this->data['sku'],
            name: (string) $this->data['name'],
            price: (string) $this->data['price'],
        ));
    } catch (DomainException $e) {
        throw new RowImportFailedException($e->getMessage());
    }

    $this->record = Product::findOrFail($result->productId); // keeps Filament's import bookkeeping consistent
}
```

Imports run in a queued job, so nobody is logged in: take the actor from `$this->import->user_id`, never `auth()`. `$this->data` holds the row after column casting/validation (`ImportColumn` rules are format validation and stay). Failed rows are downloadable by the user with your domain message. The default `saveRecord()` also saves relationships declared on `ImportColumn`s; if you override it, handle those in the use case.

## 10. Wizards and multi-step forms

Steps are UI. Validate formats per step; call the use case once, on submit, with everything. Do not persist partial state per step unless the business process genuinely has drafts — then that is its own use case (`SaveOrderDraft`).

## 11. Deletes

`DeleteAction` / `DeleteBulkAction` are fine for records with no rules. If deletion has rules (can't delete an invoiced order) or effects (release stock), use `->using()` on `DeleteAction` or a custom action calling `DeleteOrder`. Rules in a model's `deleting` observer are hidden business logic — move them to the use case.

## 12. Looks like business logic, isn't

Leave these in Filament:
- Table query scoping for display (`->modifyQueryUsing(fn ($q) => $q->where('tenant_id', ...))`), filters, sorts, search.
- Formatting (`->money()`, `->badge()`, `->formatStateUsing()` for display).
- `->options()` lists for selects, `->live()` reactivity that only changes which fields are shown.
- Format validation rules on fields.
- `->authorize()` and policies.
- Navigation badges/counts computed by a read query.

The line: *displaying and collecting* is UI; *deciding and changing* is business.
